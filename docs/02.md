# 02 — Architecture

Version: 0.1.0

---

# Overview

Vera is designed as a **modular monolith**.

All features live in one codebase while remaining isolated into independent modules.

Each module owns its own business logic, routes, services, repositories, validation, and types.

When a module grows large enough, it should be possible to extract it into its own service without changing the public API.

# Architecture Principles

Every decision inside Vera follows these principles.

* Single Responsibility
* Separation of Concerns
* Explicit Dependencies
* Composition over Inheritance
* Secure by Default
* API First
* Database Driven
* Strong Typing
* Modular Design

# Core Domain

The platform revolves around one central idea.

```text
Developer
    │
    ▼
Application
    │
    ▼
Identity
```

Everything begins with a developer.

A developer creates one or more applications.

Applications own identities.

# Primary Entities

## Developer

Represents the customer using Vera.

Responsibilities

* Owns applications
* Manages API keys
* Configures authentication
* Views analytics

---

## Application

Represents an application registered inside Vera.

Examples

* E-commerce Store
* LMS
* Mobile App
* SaaS Platform
* Marketplace

Each application has its own users, sessions, and configuration.

---

## User

Represents an authenticated identity inside an application.

Users never exist independently.

Every user belongs to exactly one application.

---

## Session

Represents an authenticated login.

A session records:

* Login time
* Device
* Browser
* IP Address
* Expiration
* Refresh Token

---

## API Key

Allows applications to communicate securely with Vera.

Two keys exist.

Public Key

Safe to expose to frontend applications.

Secret Key

Never exposed publicly.

Only servers may use secret keys.

# Module Architecture

Every module follows the same structure.

```text
modules/

auth/
│
├── auth.controller.ts
├── auth.service.ts
├── auth.repository.ts
├── auth.routes.ts
├── auth.validator.ts
├── auth.types.ts
└── index.ts
```

Every module owns everything related to itself.

No module reaches into another module's internal files.

---

# Layer Responsibilities

## Routes

Receive HTTP requests.

Responsibilities

* Register endpoints
* Call controllers

Routes contain no business logic.

---

## Controllers

Convert HTTP requests into application actions.

Responsibilities

* Read request
* Validate input
* Call service
* Return response

Controllers never access the database directly.

---

## Services

Contain business logic.

Examples

* Register developer
* Create application
* Login user
* Verify email

Services are the heart of the application.

---

## Repositories

Communicate with the database.

Responsibilities

* Query data
* Insert data
* Update data
* Delete data

Repositories never contain business rules.

---

## Prisma

Prisma is the only layer allowed to communicate directly with PostgreSQL.

No controller or route should contain raw SQL.

   ▼

---

# Error Flow

```text
Database Error
        │
        ▼
Repository
        │
        ▼
Service
        │
        ▼
Controller
        │
        ▼
Global Error Handler
        │
        ▼
HTTP Response
```

All errors should pass through one centralized error handler.

---

# Dependency Direction

Dependencies always point inward.

```text
Route
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
Prisma
```

Never reverse this dependency flow.

---

# Configuration

Application configuration belongs inside:

```text
src/config
```

Examples

* Environment variables
* Database
* JWT
* Mail
* Storage
* Logging

Configuration should never be scattered throughout the project.

---

# Shared Libraries

Reusable functionality belongs inside:

```text
src/lib
```

Examples

* Prisma Client
* Redis Client
* Mail Client
* Queue Client

---

# Utilities

Generic helper functions belong inside:

```text
src/utils
```

Examples

* Date formatting
* UUID generation
* String helpers
* Pagination

Utilities must remain framework-independent.

---

# Middleware

Middleware performs cross-cutting concerns.

Examples

* Authentication
* Authorization
* Logging
* Rate Limiting
* Error Handling
* Request Validation

Business logic does not belong inside middleware.

---

# Future Architecture

As Vera grows, new modules will be added without changing the overall architecture.

Planned modules include:

* Authentication
* Authorization
* Applications
* Organizations
* Sessions
* Roles
* Permissions
* API Keys
* Email
* Audit Logs
* OAuth
* MFA
* Notifications
* SDK Management

Each module must remain independent and follow the same architectural principles defined in this document.

---

# Architecture Goals

The architecture should remain:

* Modular
* Predictable
* Testable
* Secure
* Scalable
* Easy to understand
* Easy to maintain

Every new feature should integrate into the existing architecture without requiring structural changes.
