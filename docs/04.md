# 04 — Database Design

Version: 0.1.0

---

# Overview

This document defines the database architecture for Vera.

The database is the source of truth for the platform.

Every table, relationship, index, and constraint should be intentionally designed before implementation.

PostgreSQL is the primary database.

Prisma is the ORM responsible for communicating with PostgreSQL.

---

# Design Principles

The database should be:

* Normalized
* Predictable
* Secure
* Extensible
* Performant
* Easy to migrate

---

# Phase One Database

Only one table exists during Phase One.

```text

```

This allows the platform to establish its foundation before introducing authentication and application management.

---

# Developer Table

Purpose

Represents a developer account inside Vera.

A developer is the owner of one or more applications.

---

## Fields

| Field     | Type     | Description           |
| --------- | -------- | --------------------- |
| id        | String   | Primary identifier    |
| email     | String   | Unique email address  |
| password  | String   | Password hash         |
| createdAt | DateTime | Creation timestamp    |
| updatedAt | DateTime | Last update timestamp |

# UUID Strategy

Current implementation

```text
CUID
```

Reason

* Globally unique
* URL safe
* Easy to generate
* Prisma support

Future evaluation may compare:

* UUID v4
* UUID v7
* ULID

---

# Timestamps

Every table should include:

```text
createdAt

updatedAt
```

Optional

```text
deletedAt
```

Soft deletes should be preferred where data recovery is important.

---

# Soft Deletes

Entities should generally not be permanently removed.

Instead:

```text
deletedAt
```

A non-null value indicates the record is deleted.

Benefits

* Data recovery
* Audit history
* Compliance
* Analytics

---

# Indexing Strategy

Indexes should exist for frequently queried columns.

Examples

```text
email

applicationId

developerId

userId

sessionId
```

Avoid unnecessary indexes.

Every index increases write cost.

---

# Foreign Keys

Relationships should enforce integrity.

Example

```text
Application

developerId

↓

Developer.id
```

Never allow orphaned records.

---

# Cascading Rules

General rule

Parent deletion should not accidentally remove critical data.

Examples

Developer deleted

↓

Applications archived

↓

Users preserved until cleanup policy runs

Deletion strategies should be explicit.

# Migration Strategy

Every schema change requires a migration.

Rules

* Never edit previous migrations.
* Every migration should be reversible when possible.
* One logical change per migration.

Example

```text
001_init

002_create_applications

003_create_users

004_create_sessions
```

---

# Data Integrity Rules

* Every email must be unique within its scope.
* Every user belongs to exactly one application.
* Every application belongs to exactly one developer.
* Every session belongs to exactly one user.
* Every refresh token belongs to exactly one session.

---

# Security Considerations

Passwords

Never stored in plain text.

Always hashed.

API Keys

Secret keys should be hashed before storage where practical.

Sensitive Fields

Never expose:

* passwordHash
* refreshToken
* secretKey

Responses should only return safe data.

---

# Database Goals

The Vera database should provide:

* Strong consistency
* High integrity
* Clear relationships
* Efficient querying
* Future scalability
* Secure storage

Every future feature should extend this database without requiring a redesign of existing tables.
