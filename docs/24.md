# 24 — Rate Limiting Engine

Version: 0.1.0

---

# Overview

The Rate Limiting Engine protects Vera against abuse, brute-force attacks, denial-of-service attempts, and excessive API usage.

Every incoming request should be evaluated before business logic executes.

Rate limiting is one of the first layers of defense in the platform.

---

# Goals

The Rate Limiting Engine should provide:

* Request throttling
* Abuse prevention
* Brute-force protection
* Configurable limits
* Distributed rate limiting
* Multiple limiting strategies
* Usage tracking

---

# Responsibilities

The Rate Limiting Engine is responsible for:

* Counting requests
* Enforcing request limits
* Blocking abusive clients
* Resetting counters
* Returning limit information
* Recording violations

It is **not** responsible for authentication or authorization.

---

# Design Philosophy

Every client should receive fair access to platform resources.

No client should be capable of degrading service for others.

---

# Request Flow

```text id="rate01"
Incoming Request

↓

Identify Client

↓

Find Applicable Rule

↓

Increment Counter

↓

Limit Exceeded?

↓

Yes → Reject Request

↓

No → Continue Processing
```

```text id="rate02"
User ID
```

# Rate Limit Strategies

Supported strategies

```text id="rate03"
Fixed Window

Sliding Window

Sliding Log

Token Bucket

Leaky Bucket
```

---

# Initial Strategy

Version 1 should implement

```text id="rate04"
Sliding Window
```

Reasons

* Fair distribution
* Accurate counting
* Reduced burst abuse
* Widely adopted

---

# Default Limits

Suggested defaults

| Resource           |               Limit |
| ------------------ | ------------------: |
| Public API         | 100 requests/minute |
| Auth Endpoints     |  10 requests/minute |
| Password Reset     |     5 requests/hour |
| Email Verification |     5 requests/hour |
| API Key Creation   |    20 requests/hour |

Limits should be configurable.

# Response Headers

Successful responses should include

```text id="rate09"
X-RateLimit-Limit

X-RateLimit-Remaining

X-RateLimit-Reset
```

These headers help clients avoid exceeding limits.

---

# Limit Exceeded

When a limit is exceeded

Response

```http id="rate10"
429 Too Many Requests
```

Example

```json id="rate11"
{
  "success": false,
  "message": "Rate limit exceeded.",
  "retryAfter": 60
}
```

---

# Retry Information

Clients should receive

* Retry duration
* Remaining wait time
* Limit information

This improves client behavior and user experience.

# Authentication Protection

Sensitive endpoints require stricter limits.

Examples

* Login
* Registration
* Password Reset
* Email Verification
* Token Refresh

---

# API Key Protection

Separate limits should exist for API key usage.

Limits may depend on

* Plan
* Application
* Environment
* Organization

---

# Burst Handling

Short bursts should be tolerated within configured thresholds.

Long-term abuse should always be blocked.

---

# Whitelisting

Trusted clients may bypass limits.

Examples

```text id="rate15"
Internal Services

System Workers

Health Checks
```

---

# Blacklisting

Repeated abuse may result in temporary blocking.

Possible actions

```text id="rate16"
Temporary Ban

Permanent Ban

Challenge Verification
```

# Monitoring

Track

* Requests per second
* Rate limit violations
* Top endpoints
* Top blocked clients
* Average request rate

---

# Alerting

Generate alerts when

* Brute-force attacks increase
* API abuse spikes
* Large numbers of blocked requests occur
* Redis becomes unavailable

---

# Failure Policy

If Redis becomes unavailable

```text id="rate19"
Redis Failure

↓

Fallback Policy

↓

Temporary In-Memory Limiting

↓

Restore Redis

↓

Resume Normal Operation
```

The API should remain operational whenever possible.

---

# Security

The Rate Limiting Engine should

* Prevent brute-force attacks
* Slow credential stuffing
* Protect expensive endpoints
* Prevent denial-of-service amplification
* Integrate with the Audit Engine

---

# Integration

The Rate Limiting Engine integrates with

* Authentication Engine
* API Key Engine
* Session Engine
* Audit Engine
* Monitoring Engine
* Logging Engine

Every incoming request should pass through the Rate Limiting Engine before reaching application logic.

---

# Design Goals

The Rate Limiting Engine should provide fast, scalable, and configurable protection against abuse while maintaining fair access for legitimate clients.

It should support both small deployments and distributed production environments without requiring changes to application code.
