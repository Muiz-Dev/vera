# 03 — Project Structure

Version: 0.1.0

---

# Overview

This document defines the directory structure of Vera.

Every folder has a single responsibility.

A predictable structure makes the project easier to maintain, easier to onboard new developers, and easier to scale as new features are added.

No file should exist without a clear purpose.

---

# Root Structure

```text
vera/
│
├── docs/
├── prisma/
├── src/
├── tests/
│
├── .env
├── .env.example
├── .gitignore
├── package.json
├── prisma.config.ts
├── tsconfig.json
└── README.md
```

---

# Root Directory Responsibilities

## docs/

Contains all project documentation.

Examples

```text
docs/

01-vision.md
02-architecture.md
03-project-structure.md
04-database.md
05-api.md
06-security.md
07-roadmap.md
08-coding-standards.md
09-contributing.md
10-decisions.md
```

No source code belongs here.

---

## prisma/

Contains everything related to Prisma.

```text
prisma/

schema.prisma

migrations/
```

Responsibilities

* Database schema
* Database migrations

Only Prisma files belong here.

---

## src/

Contains the entire application source code.

Everything executed by Node.js lives inside this directory.

---

## tests/

Contains automated tests.

Examples

```text
tests/

unit/

integration/

e2e/
```

Application code must never be placed inside this directory.

---

# Source Structure

```text
src/

config/
core/
generated/
lib/
middlewares/
modules/
routes/
types/
utils/

app.ts
server.ts
```

---

# app.ts

Purpose

Application configuration.

Responsibilities

* Create Express application
* Register middleware
* Register routes
* Configure JSON parser
* Configure error handling

The server should never start inside this file.

---

# server.ts

Purpose

Application entry point.

Responsibilities

* Import app
* Read environment variables
* Start HTTP server
* Display startup information

Nothing else belongs here.

---

# config/

Contains application configuration.

Examples

```text
config/

database.ts
environment.ts
logger.ts
mail.ts
storage.ts
```

Configuration should never be duplicated elsewhere.

---

# core/

Contains framework-independent core functionality.

Examples

```text
core/

errors/

events/

constants/

responses/
```

Core code should be reusable across modules.

---

# generated/

Contains generated code.

Currently

```text
generated/

prisma/
```

Never modify generated files manually.

Generated files may be safely deleted and recreated.

---

# lib/

Contains initialized clients.

Examples

```text
lib/

prisma.ts

redis.ts

mailer.ts

storage.ts
```

Responsibilities

* Create clients
* Configure clients
* Export initialized instances

No business logic belongs here.

---

# middlewares/

Contains Express middleware.

Examples

```text
middlewares/

auth.middleware.ts

error.middleware.ts

logger.middleware.ts

rate-limit.middleware.ts
```

Each middleware performs exactly one responsibility.

---

# modules/

The heart of Vera.

Every feature is implemented as a module.

Example

```text
modules/

auth/

developers/

applications/

users/

sessions/
```

Modules should never depend on each other's internal implementation.

Communication happens through exported services.

---

# Module Layout

Each module follows the same structure.

```text
applications/

application.controller.ts

application.service.ts

application.repository.ts

application.routes.ts

application.validator.ts

application.types.ts

index.ts
```

Every module owns:

* Routes
* Controllers
* Services
* Repositories
* Validation
* Types

This keeps features isolated.

---

# Routes

Purpose

Register HTTP endpoints.

Example

```text
GET /applications

POST /applications
```

Routes only forward requests.

No business logic.

---

# Controllers

Purpose

Translate HTTP requests into service calls.

Responsibilities

* Read request
* Validate request
* Call service
* Return response

Controllers do not access Prisma directly.

---

# Services

Purpose

Implement business rules.

Examples

```text
Create Application

Delete Application

Create Session

Verify Password

Issue Token
```

Every business rule belongs inside a service.

---

# Repositories

Purpose

Communicate with the database.

Responsibilities

* Queries
* Inserts
* Updates
* Deletes

Repositories contain no business decisions.

---

# Validators

Purpose

Validate incoming data.

Examples

```text
Email

Password

UUID

Slug

Application Name
```

Validation happens before business logic.

---

# Types

Purpose

Store shared TypeScript types.

Examples

```text
ApplicationDTO

DeveloperDTO

UserDTO

LoginRequest

RegisterRequest
```

Avoid duplicated interfaces.

---

# routes/

Registers every module.

Example

```text
routes/

index.ts
```

Responsibilities

* Import module routes
* Register API versions
* Organize endpoints

No business logic.

---

# utils/

Reusable helper functions.

Examples

```text
utils/

slug.ts

pagination.ts

date.ts

crypto.ts
```

Utilities should be generic.

They should not depend on Express or Prisma.

---

# types/

Global project types.

Examples

```text
types/

express.d.ts

environment.ts

pagination.ts
```

Shared across multiple modules.

---

# Environment Files

```text
.env

.env.example
```

Rules

Never commit `.env`.

Always commit `.env.example`.

---

# Generated Files

Do not edit:

```text
generated/

node_modules/

dist/
```

These are recreated automatically.

---

# Naming Convention

Folders

```text
lowercase
```

Example

```text
applications
```

Files

```text
kebab-case
```

Examples

```text
application.service.ts

auth.controller.ts

error.middleware.ts
```

Classes

```text
PascalCase
```

Example

```text
ApplicationService
```

Variables

```text
camelCase
```

Constants

```text
UPPER_SNAKE_CASE
```

---

# Import Rules

Preferred

```text
Controller

↓

Service

↓

Repository

↓

Prisma
```

Avoid circular dependencies.

Modules should communicate through exported interfaces.

---

# Project Growth

As Vera grows, only the `modules/` directory should expand significantly.

The root architecture should remain stable.

Future modules include

* Authentication
* Authorization
* Applications
* Organizations
* Sessions
* Roles
* Permissions
* API Keys
* Audit Logs
* Notifications
* OAuth
* MFA
* Webhooks
* SDKs

No structural redesign should be necessary to support future features.

---

# Summary

The project structure is designed to achieve:

* Predictability
* Maintainability
* Scalability
* Separation of concerns
* Consistent development practices

Every new file added to Vera should fit naturally into this structure without introducing ambiguity or duplication.
