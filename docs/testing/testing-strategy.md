# Vera Testing Architecture & Long-Term Strategy

This document outlines Vera's architectural testing roadmap and verification gates. Our strategy balances developers' feedback loops, integration safety, programmatic correctness, and enterprise validation.

---

## 1. Multi-Tiered Testing Pyramid

To ensure the platform scale reliably and with minimal regressions, Vera will implement a tiered testing hierarchy progressively as the product grows:

```
                  /\
                 /  \      E2E Tests (Playwright / Cypress)
                /----\
               /      \    Integration Tests (Custom HTTP, API-bound)
              /--------\
             /          \  Unit Tests (Vitest, Fast Isolated Logic)
            /------------\
```

### Layer 1: Unit Tests (Target: PR #010–#015)
- **Tooling:** Vitest (for ESModule compatibility, extreme speeds, and isolation).
- **Scope:** Complete separation from external systems (no database, no network).
- **Core Targets:** Custom validation schemas, configuration parsers, event registry bindings, helper packages, policy calculation engines.

### Layer 2: Integration Tests (Current)
- **Tooling:** Custom Lightweight HTTP Integration Runner.
- **Scope:** Verifies that modular routing layers, services, database configurations, transactions, hashing, and event propagation are fully functioning together.
- **Prerequisite:** Freshly connected, non-production test PostgreSQL instance.
- **State Management:** Strict, deterministic setup and teardown tasks via helper utilities.

### Layer 3: End-to-End (E2E) Tests
- **Tooling:** Playwright.
- **Scope:** Complex user journeys and frontend verification across systems.
- **Targets:** Entire registration pipelines, multi-factor logins, multi-tenant workspace setups.

## 2. Specialized Testing Pillars

Beyond core functional verification, Vera's engineering standards encompass additional specialized testing vectors:

### Pillar A: Security Verification
- **Replay Protection:** Ensuring refresh tokens can never be reused; replay scenarios trigger immediate revocation of the entire session cascade.
- **Account Enumeration Defenses:** Forgot-password endpoints and invalid logins must return uniform response delays and envelopes to prevent timing attacks.
- **Argon2id Integrity:** Ensure password credentials are cryptographically safe and validated with appropriate constant-time functions.

### Pillar B: Eventual Consistency & Domain Event Testing
- **Event Bus Assertions:** Programmatically subscribe to and verify the payload schema of events (`IdentityCreated`, `EmailVerificationRequested`, `RefreshTokenRotated`, etc.) generated by service-level actions.

### Pillar C: Performance & Load Testing (Future Phase)
- **Tooling:** k6.
- **Scope:** Verify platform latency, response durations under load, database pool constraints, and garbage collection metrics.

---

## 3. The Vera Quality Gate (Continuous Integration)

The long-term objective for Vera is that every single pull request can be fully validated locally and in CI/CD with a single unified entry command:

```bash
npm run verify
```

This single command triggers an automated pipeline:
1. **Linter Checklist:** Confirms code styling and syntactical formatting.
2. **Type Checking:** Runs `tsc --noEmit` to verify type safety.
3. **Prisma Generation:** Validates current schema matches code models.
4. **Integration Testing:** Bootstraps custom integration suite on test DB.
5. **Coverage Gates:** Ensures coverage remains above defined threshold (e.g., 90%).
6. **Report Logging:** Generates formal markdown quality reports.

The command will fail immediately if any of these checkpoints do not pass, protecting the stability of the master branches.
