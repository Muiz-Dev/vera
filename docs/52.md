# Overview

The JWT Engine is responsible for generating, signing, validating, decoding, rotating, and managing **JSON Web Tokens (JWTs)** throughout the Vera platform.

While the **Token Engine** manages the lifecycle of all token types, the JWT Engine specifically implements the **RFC 7519 JSON Web Token** standard.

JWTs provide compact, self-contained, cryptographically signed tokens that enable secure identity propagation between services without requiring database lookups for every request.

The JWT Engine serves as the primary token implementation for authentication, authorization, APIs, SDKs, internal microservices, and external integrations.

# Core Principles

## Standards Compliance

The JWT Engine follows

* RFC 7519 (JWT)
* RFC 7515 (JWS)
* RFC 7517 (JWK)
* RFC 7518 (JWA)
* RFC 8725 (JWT Best Current Practices)

---

## Signed, Not Trusted

Every received JWT must be verified.

Decoding a JWT without verifying its signature must never be treated as authentication.

---

## Immutable Payload

Once issued, JWT payloads cannot be modified.

Any change requires issuance of a new token.

---

## Short-Lived Access Tokens

JWT Access Tokens should have short expiration periods.

Recommended lifetime

```text id="jwt01"
15 Minutes
```

---

## Stateless by Design

JWT validation should not require a database lookup unless revocation or advanced policies require it.

# Validation Rules

* Every JWT requires a valid signature.
* Expired JWTs are rejected.
* Unsupported algorithms are rejected.
* Audience must match the target service.
* Issuer must be trusted.
* JWT IDs must be unique.

# Security

The JWT Engine must

* Reject unsigned JWTs
* Reject `alg=none`
* Prevent algorithm confusion attacks
* Support secure key rotation
* Protect private signing keys
* Validate every registered claim
* Enforce trusted issuers

# Architecture Decision Record (ADR-012)

**Decision:** Vera adopts signed JWTs using modern asymmetric cryptography as the primary stateless token format for distributed authentication and authorization.

**Reason:** Asymmetric signatures improve security, simplify verification across services, eliminate shared-secret distribution challenges, and provide compatibility with industry standards and third-party integrations.

**Consequences:**

* Services verify tokens using public keys.
* Private signing keys remain protected.
* Stateless verification reduces database dependency.
* Future OpenID Connect support integrates naturally through JWKS.

---

# Design Goals

The JWT Engine provides Vera's standards-compliant implementation of JSON Web Tokens, delivering secure, high-performance, stateless identity propagation across distributed systems.

Its architecture emphasizes cryptographic integrity, interoperability, scalable verification, secure key management, and seamless integration with the Token Engine, Authentication Engine, OAuth Engine, API Gateway, and every service that relies on trusted, verifiable identity tokens.
