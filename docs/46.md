# 46 — Permission Engine

Version: 1.0.0

Owner: Vera Core Team

# Overview

The Permission Engine defines **what actions can be performed** within the Vera platform.

While the **Role Engine** defines *who a user is*, the **Permission Engine** defines *what that identity is allowed to do*.

Permissions are atomic, reusable capabilities that can be assigned to Roles. The Authorization Engine evaluates these permissions during every protected operation.

The Permission Engine provides the lowest level of access control across Vera.

---

# Objectives

The Permission Engine provides:

* Permission definition
* Permission management
* Permission grouping
* Permission assignment
* Permission inheritance support
* Resource-action modeling
* Permission versioning
* Permission auditing
* Fine-grained authorization
* Cross-engine permission registry

---

# Vision

Every action inside Vera should be protected by one or more explicit permissions.

No endpoint, API, service, or resource should rely solely on frontend restrictions or implicit trust.

---

# Core Principles

## Atomic Permissions

Each permission represents exactly one capability.

Examples

```text id="perm01"
application.create

application.delete

organization.update

apikey.rotate
```

---

## Permissions Are Reusable

One permission may be assigned to many roles.

```text id="perm02"
Permission

↓

Administrator

Developer

Owner
```

---

## Resource-Based

Every permission follows

```text id="perm03"
resource.action
```

Example

```text id="perm04"
application.create

application.read

application.update

application.delete
```

---

## Independent

Permissions do not reference users.

Permissions describe capabilities only.

---

## Extensible

New platform features should introduce new permissions without modifying existing ones.

---

# Responsibilities

The Permission Engine is responsible for

* Creating permissions
* Updating permissions
* Organizing permissions
* Permission metadata
* Permission discovery
* Permission documentation
* Permission auditing
* Permission registry

The Permission Engine is NOT responsible for

* Role assignment
* Authentication
* Session validation
* Runtime authorization decisions

# Architecture Decision Record (ADR-006)

**Decision:** Permissions are stored as independent, atomic capabilities using the `resource.action` convention.

**Reason:** Atomic permissions provide maximum flexibility, simplify auditing, encourage reuse across roles, and support future authorization models such as RBAC, ABAC, and policy-based access control without redesigning the permission registry.

**Consequences:**

* Every protected operation maps to one or more permissions.
* Roles become collections of permissions.
* Authorization logic remains centralized.
* New platform features introduce permissions without affecting existing roles.

---

# Design Goals

The Permission Engine establishes the fundamental capability model of Vera by defining every action that can be performed across the platform.

It provides a centralized, scalable, and extensible permission registry that supports fine-grained authorization, strong security, comprehensive auditing, and seamless integration with the Role Engine and Authorization Engine, ensuring every protected resource is governed by explicit and verifiable access rules.
