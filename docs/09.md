# 09 — Contributing Guide

Version: 0.1.0

---

# Overview

This document defines how developers contribute to Vera.

The objective is to ensure every contribution is consistent, maintainable, secure, and aligned with the project's long-term vision.

Every contribution should improve the project—not just add features.

---

# Philosophy

Vera values:

* Simplicity
* Consistency
* Security
* Documentation
* Maintainability
* Long-term thinking

Every pull request should move the project closer to these goals.

---

# Before You Contribute

Before writing code:

* Read the project documentation.
* Understand the architecture.
* Check existing issues.
* Confirm the feature belongs in the current roadmap phase.
* Search for existing implementations.

Do not start coding before understanding the problem.

---

# Local Setup

Clone the repository.

```bash
git clone <repository-url>

cd vera
```

Install dependencies.

```bash
npm install
```

Configure environment variables.

```text
cp .env.example .env
```

Generate Prisma Client.

```bash
npx prisma generate
```

Run migrations.

```bash
npx prisma migrate dev
```

Start the development server.

```bash
npm run dev
```

---

# Branch Strategy

Never commit directly to the main branch.

Create a feature branch.

Examples

```text
feature/auth

feature/applications

feature/sessions

feature/roles

feature/oauth
```

Bug fixes

```text
fix/login

fix/database

fix/api
```

Documentation

```text
docs/security

docs/database

docs/api
```

Refactoring

```text
refactor/prisma

refactor/controllers
```

---

# Commit Messages

Use Conventional Commits.

Examples

```text
feat(auth): implement developer registration

feat(users): add refresh token support

fix(database): resolve migration issue

fix(api): validate request payload

refactor(auth): simplify login flow

docs(api): update authentication endpoints

test(users): add integration tests

chore(deps): update Prisma
```

Avoid vague commit messages.

Bad

```text
update

fix

changes

done

working

again
```

---

# Pull Request Requirements

Every pull request should contain:

* Purpose
* Summary
* Related Issue
* Database Changes
* Testing Information
* Documentation Updates

Example

```text
Purpose

Implement developer registration.

Changes

- Added DeveloperService
- Added validation
- Added migration
- Added repository
- Added API endpoint

Testing

- Unit tests passed
- Manual testing completed

Documentation

- API updated
- Database updated
```

---

# Code Review Checklist

Before approving a pull request, verify:

* Architecture is respected.
* Coding standards are followed.
* Business logic is in services.
* Database access is in repositories.
* Validation exists.
* Errors are handled.
* No secrets are committed.
* Documentation is updated.

---

# Database Contributions

Rules

* Never edit old migrations.
* Create a new migration for every schema change.
* Keep migrations small.
* Name migrations clearly.

Example

```text
create_developers

create_applications

add_email_verification

create_sessions
```

---

# API Contributions

Every new endpoint requires:

* Request validation
* Response documentation
* Error responses
* Authentication requirements
* Status codes

No endpoint should be merged without documentation.

---

# Security Contributions

Changes affecting authentication, authorization, sessions, cryptography, or secrets require additional review.

Examples

* Password hashing
* JWT
* OAuth
* Session management
* API Keys
* MFA

Security-related pull requests should explain *why* the implementation is secure.

---

# Testing Requirements

Every new feature should include appropriate tests.

Testing hierarchy

```text
Unit Tests

↓

Integration Tests

↓

End-to-End Tests
```

Critical authentication features require all three.

---

# Documentation Requirements

Documentation must stay synchronized with implementation.

If you modify:

* API
* Database
* Architecture
* Security
* Project Structure

Update the relevant document in `/docs`.

Code without documentation is considered incomplete.

---

# Dependency Policy

Before adding a dependency, ask:

* Is it actively maintained?
* Is it secure?
* Is it necessary?
* Does it duplicate existing functionality?
* Is there a lighter alternative?

Every dependency increases maintenance cost.

---

# Performance Guidelines

When contributing:

* Avoid unnecessary database queries.
* Prevent N+1 query problems.
* Minimize memory allocations.
* Use indexes where appropriate.
* Keep API responses efficient.

Performance should be considered during implementation, not after release.

---

# Error Handling

Errors should:

* Be predictable.
* Be logged.
* Never expose internal implementation details.
* Return meaningful HTTP status codes.

Stack traces should never be returned in production responses.

---

# Versioning

Vera follows Semantic Versioning.

```text
MAJOR.MINOR.PATCH
```

Example

```text
1.0.0
```

* MAJOR — Breaking changes
* MINOR — New functionality
* PATCH — Bug fixes

---

# Release Process

Every release should include:

* Updated version number
* Migration review
* Documentation review
* Changelog update
* Passing tests

Only tagged releases should be considered stable.

---

# Issue Reporting

Bug reports should include:

* Description
* Steps to reproduce
* Expected behavior
* Actual behavior
* Environment
* Logs (if applicable)

Feature requests should include:

* Problem statement
* Proposed solution
* Expected benefit
* Possible alternatives

---

# Community Standards

Contributors should:

* Be respectful.
* Provide constructive feedback.
* Review code objectively.
* Discuss ideas with evidence.
* Focus on improving the project.

Technical discussions should remain professional.

---

# Long-Term Vision

Vera is intended to become a production-grade identity platform.

Every contribution should support that vision by improving:

* Reliability
* Security
* Scalability
* Developer Experience
* Maintainability

---

# Definition of a Good Contribution

A good contribution:

* Solves a real problem.
* Follows the architecture.
* Includes tests.
* Includes documentation.
* Does not introduce unnecessary complexity.
* Leaves the codebase cleaner than it was before.

---

# Final Principle

> Write code as if someone else will maintain it in five years. Make that person's job easier, not harder.
