# Overview

The Access Token Engine is responsible for issuing, validating, managing, and revoking short-lived Access Tokens used to authorize requests across the Vera platform.

An Access Token represents an authenticated identity together with its authorized permissions for a limited period of time.

Unlike Refresh Tokens, Access Tokens are presented to APIs, gateways, microservices, SDKs, and internal platform services during every authenticated request.

The Access Token Engine prioritizes high performance, cryptographic integrity, minimal latency, and seamless interoperability across Vera's distributed architecture.

# Vision

Every authenticated request processed by Vera should be authorized through a secure, short-lived Access Token that can be verified efficiently while maintaining strong security guarantees.

---

# Core Principles

## Short Lifetime

Access Tokens should expire quickly.

Recommended lifetime

| Token Type | Lifetime     |
| ---------- | ------------ |
| Web        | 15 Minutes   |
| Mobile     | 15 Minutes   |
| CLI        | 10 Minutes   |
| Service    | 5–15 Minutes |

---

## Stateless Validation

Most Access Tokens should be verifiable without requiring database access.

Stateless verification improves scalability and reduces latency.

---

## Least Privilege

Access Tokens should contain only the permissions required by the requesting application.

---

## Audience Restricted

Each Access Token is valid only for its intended audience.

Example

```text id="access01"
Billing API

Storage API

Identity API

Deployment API
```

---

## Immutable

An Access Token cannot be modified after issuance.

Changes require issuance of a completely new token.

---

# Responsibilities

The Access Token Engine is responsible for

* Token issuance
* Token validation
* Scope embedding
* Audience enforcement
* Expiration handling
* Token introspection
* Security metadata
* Usage analytics

The Access Token Engine is NOT responsible for

* User authentication
* Password verification
* Refresh Token rotation
* OAuth consent
* Session creation

# Expiration

Expired Access Tokens

* Cannot be refreshed directly
* Cannot access APIs
* Must be replaced using a valid Refresh Token

---

# Revocation

Although Access Tokens are intentionally short-lived, revocation may occur for

* Account compromise
* Administrator action
* Device compromise
* Password reset
* Session termination

Revocation data is maintained by the Token Engine.

# Architecture Decision Record (ADR-014)

**Decision:** Vera uses short-lived, stateless Access Tokens as the primary authorization credential for APIs and distributed services.

**Reason:** Short-lived Access Tokens reduce security risk, improve scalability through stateless validation, and align with modern authentication architectures built on OAuth 2.1 and zero-trust principles.

**Consequences:**

* APIs perform fast local verification.
* Authentication servers avoid unnecessary database lookups.
* Compromised tokens have limited usefulness.
* Refresh Tokens remain responsible for long-term session continuity.

---

# Design Goals

The Access Token Engine provides Vera's high-performance authorization credential infrastructure by issuing secure, short-lived tokens that enable efficient access to protected resources across distributed services.

Its architecture emphasizes low-latency validation, cryptographic integrity, fine-grained authorization, interoperability with industry standards, and seamless integration with the Token Engine, JWT Engine, Authorization Engine, API Gateway, and the broader Vera platform.
