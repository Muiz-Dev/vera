# 08 — Coding Standards

Version: 0.1.0

---

# Overview

This document defines the engineering standards for Vera.

Every contributor must follow these standards to ensure the codebase remains consistent, maintainable, and scalable.

Code is read far more often than it is written.

Write code for humans first.

---

# Core Principles

Every piece of code should be:

* Readable
* Predictable
* Maintainable
* Testable
* Secure
* Explicit
* Consistent

Never optimize for cleverness.

Optimize for clarity.

---

# General Rules

* Keep functions small.
* Keep files focused.
* Avoid duplication.
* Prefer composition over inheritance.
* Write descriptive names.
* Never ignore errors.
* Remove dead code.
* Delete unused imports.
* Never commit commented-out code.

---

# Naming Conventions

## Variables

Use camelCase.

```ts id="cs01"
const developerId = "...";
const refreshToken = "...";
const createdAt = new Date();
```

---

## Functions

Use verbs.

```ts id="cs02"
createDeveloper()

loginDeveloper()

generateAccessToken()

verifyPassword()

createSession()
```

Avoid names like:

```ts id="cs03"
doStuff()

handle()

process()

run()
```

---

## Classes

Use PascalCase.

```ts id="cs04"
DeveloperService

ApplicationRepository

SessionController
```

---

## Interfaces

Use PascalCase.

```ts id="cs05"
Developer

Application

CreateUserRequest
```

Avoid prefixing with `I`.

Bad

```ts id="cs06"
IDeveloper
```

---

## Constants

Use UPPER_SNAKE_CASE.

```ts id="cs07"
MAX_LOGIN_ATTEMPTS

DEFAULT_PAGE_SIZE

TOKEN_EXPIRATION
```

---

## Files

Use kebab-case.

```text id="cs08"
developer.service.ts

auth.controller.ts

password.validator.ts
```

---

## Folders

Use lowercase.

```text id="cs09"
modules

middlewares

config

utils
```

---

# Project Structure

Every feature belongs inside a module.

Example

```text id="cs10"
developers/

developer.controller.ts

developer.service.ts

developer.repository.ts

developer.routes.ts

developer.validator.ts

developer.types.ts
```

Never place unrelated logic inside a module.

---

# Import Order

Imports should always follow the same order.

```ts id="cs11"
import fs from "fs";

import express from "express";

import { PrismaClient } from "...";

import { createToken } from "...";

import "./config";
```

Order

1. Node.js
2. External packages
3. Internal modules
4. Relative imports

---

# Function Design

A function should perform one task.

Good

```ts id="cs12"
createDeveloper()
```

Bad

```ts id="cs13"
createDeveloperAndSendEmailAndCreateSession()
```

Split responsibilities.

---

# Function Length

Recommended

Less than 40 lines.

Maximum

100 lines.

If a function exceeds this, consider extracting helper functions.

---

# Class Responsibilities

Each class should have one responsibility.

Good

```text id="cs14"
DeveloperService

ApplicationService

EmailService
```

Avoid large "God Classes."

---

# Routes

Routes should only:

* Define endpoints
* Register middleware
* Call controllers

Never place business logic inside routes.

Bad

```ts id="cs15"
router.post("/login", async () => {
    // authentication logic
});
```

Good

```ts id="cs16"
router.post("/login", loginController);
```

---

# Controllers

Controllers should:

* Read request
* Validate request
* Call service
* Return response

Controllers should never:

* Query Prisma
* Hash passwords
* Generate JWTs

---

# Services

Services contain business logic.

Examples

```text id="cs17"
Login

Registration

Email Verification

Password Reset
```

Every business rule belongs here.

---

# Repositories

Repositories communicate with Prisma.

Responsibilities

* Find
* Create
* Update
* Delete

Repositories should never contain business decisions.

---

# Validation

Validate everything.

Examples

* Email
* Password
* UUID
* Pagination
* Query parameters

Never trust client input.

---

# Error Handling

Never expose internal errors.

Bad

```json id="cs18"
{
    "message": "Prisma error..."
}
```

Good

```json id="cs19"
{
    "message": "Internal server error."
}
```

Log internal details privately.

---

# Async Code

Always use async/await.

Avoid nested promise chains.

Good

```ts id="cs20"
const user = await repository.findByEmail(email);
```

---

# Comments

Write comments only when necessary.

Avoid explaining obvious code.

Bad

```ts id="cs21"
// increment counter
counter++;
```

Good

Explain business rules or non-obvious decisions.

---

# Logging

Log important events.

Good

* Login
* Logout
* Failed Login
* Password Reset
* API Key Rotation

Do not log:

* Passwords
* Tokens
* Secrets

---

# Environment Variables

Never hardcode secrets.

Bad

```ts id="cs22"
const secret = "123456";
```

Good

```ts id="cs23"
process.env.JWT_SECRET
```

---

# Database Access

Only repositories communicate with Prisma.

Never call Prisma inside:

* Routes
* Controllers
* Middleware

---

# API Responses

Always return a consistent structure.

Success

```json id="cs24"
{
    "success": true,
    "message": "Developer created.",
    "data": {}
}
```

Failure

```json id="cs25"
{
    "success": false,
    "message": "Validation failed.",
    "errors": []
}
```

---

# Git Commits

Use meaningful commit messages.

Good

```text id="cs26"
feat(auth): implement developer registration

fix(api): validate email input

refactor(database): simplify repository

docs: update roadmap
```

Avoid

```text id="cs27"
update

fix

changes

work
```

---

# Branch Naming

Examples

```text id="cs28"
feature/auth

feature/sessions

fix/login

refactor/database

docs/security
```

---

# Dependencies

Before adding a dependency ask:

* Is it maintained?
* Is it secure?
* Can we implement this ourselves?
* Is it actively used?
* Does it solve a real problem?

Avoid unnecessary dependencies.

---

# Testing Standards

Every feature should include:

* Unit Tests
* Integration Tests

Critical authentication flows should include end-to-end tests.

---

# Documentation

Every public module should be documented.

Every major architectural decision should be recorded.

Documentation is part of the implementation.

---

# Pull Request Checklist

Before merging:

* Code builds successfully.
* Tests pass.
* Documentation updated.
* No lint errors.
* No secrets committed.
* No debug code.
* No commented code.
* API documented.
* Migration reviewed.

---

# Engineering Philosophy

The Vera codebase should feel predictable.

A developer opening any module should immediately understand:

* Where logic lives
* How data flows
* How errors are handled
* How modules communicate

Consistency is more valuable than personal coding style.

---

# Final Principle

> Every line of code added to Vera should make the project easier to understand, easier to extend, and harder to misuse.
