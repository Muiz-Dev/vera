# 14 — API Key Engine

Version: 0.1.0

---

# Overview

The API Key Engine manages how applications securely authenticate with Vera.

While users authenticate with credentials such as passwords or OAuth providers, applications authenticate using API keys.

Every application created in Vera receives its own credentials.

---

# Goals

The API Key Engine should provide:

* Secure application authentication
* API key generation
* API key rotation
* API key revocation
* Permission scoping
* Usage tracking
* Secure storage

---

# Responsibilities

The API Key Engine is responsible for:

* Creating API keys
* Validating API keys
* Rotating API keys
* Revoking API keys
* Tracking API usage
* Enforcing application ownership

It is not responsible for authenticating end users.

---

# API Key Types

Every application receives two credentials.

```text id="api01"
Public Key

Secret Key
```

---

# Public Key

Purpose

Identifies the application.

Characteristics

* Safe for frontend use
* Not confidential
* Used as the application identifier

Example

```text id="api02"
pk_live_xxxxxxxxxxxxxxxxx
```

---

# Secret Key

Purpose

Authenticates the application.

Characteristics

* Server-side only
* Never exposed to browsers
* Never embedded in mobile apps
* Never committed to Git

Example

```text id="api03"
sk_live_xxxxxxxxxxxxxxxxx
```

---

# API Key Lifecycle

```text id="api04"

↓

Generate Keys

↓

Store Secret

↓

Application Uses Key

↓

Rotate (Optional)

↓

Revoke

↓

Generate Replacement
```

---

# Key Generation

API keys should be:

* Cryptographically secure
* Random
* Globally unique
* Difficult to guess

Keys should never follow predictable patterns.

---

# Storage

Public keys may be stored in plain text.

Secret keys should be stored as hashes whenever possible.

Pipeline

```text id="api05"
Secret Key

↓

Hash

↓

Database
```

The original secret should only be shown once at creation.

---

# Key Prefixes

Recommended prefixes

Development

```text id="api06"

sk_test_
```

Production

```text id="api07"

sk_live_
```

Prefixes make keys immediately identifiable.


---

# Key Rotation

Applications should be able to rotate keys without downtime.

Rotation process

```text id="api09"
Generate New Key

↓

Keep Previous Key Active

↓

Application Updates Configuration

↓

Deactivate Old Key

↓

Delete Old Key
```

Temporary overlap reduces service interruptions.

---

# Revocation

Revoked keys become immediately invalid.

Reasons

* Secret leaked
* Key compromised
* Application deleted
* Manual revocation

Revoked keys cannot be restored.

---

# Permissions

API keys may eventually support scoped permissions.

Examples

```text id="api10"
users.read

users.write

sessions.read

sessions.revoke
```

Applications should receive only the permissions they require.

# Request Authentication

Applications authenticate using headers.

Example

```http id="api18"
Authorization: Bearer sk_live_xxxxxxxxx
```

Alternative headers may be supported in SDKs.

---

# Usage Tracking

Every API key should record:

* Last used
* Total requests
* Failed requests
* IP address (optional)
* Environment
* Application ID

This information assists with monitoring and incident response.

---

# Rate Limiting

Rate limits may be enforced per API key.

Benefits

* Prevent abuse
* Protect infrastructure
* Ensure fair usage

Future plans may introduce configurable limits.

---

# Security Rules

API keys must:

* Be generated using a cryptographically secure random source
* Never be logged
* Never appear in URLs
* Never be sent over HTTP
* Never be exposed in client-side code
* Support immediate revocation

# Design Goals

The API Key Engine should provide a secure, scalable, and developer-friendly method for authenticating applications.

API keys should be easy to manage, simple to rotate, safe to revoke, and designed to minimize the impact of credential compromise while supporting future enterprise features.
